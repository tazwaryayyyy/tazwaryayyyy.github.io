1.Abstract

Verification-Guided Curriculum Learning (VGCL) asks whether failure-targeted verified synthetic curricula produce better capability transfer than uniformly sampled verified synthetic curricula under equal compute budgets. This document records the final state of the VGCL_Pipeline repository across its V7 experimental freeze (11 September 2026) and its V8 execution-security freeze (19 November 2026).

The pipeline splits work across two environments: local problem generation, repair, and behavioral verification, followed by remote probing of a small base model to observe where it fails, followed by local ingestion, target checks, and eligibility gating. Successive audits of earlier versions found label-only targeting, synthetic difficulty assignment, drift between treatment and control cohorts, fallback-model contamination, calibration-evaluation leakage, and untrusted code execution inside model-owning and verification processes. Each issue was patched in later revisions, ending with V7's eligibility and provenance layer and V8's sandbox isolation.

Software regression suites verify that the code gates, serialization boundaries, and sandbox isolation behave as implemented. Those tests say nothing about model capability or curriculum effectiveness. Because no treatment and control training comparison was ever completed, the central empirical question remains unresolved.

2.Research question and hypothesis

VGCL is designed to test one empirical question: under equal compute budgets, does a verified synthetic programming curriculum targeted at a base model's observed failures transfer capability better than a verified synthetic curriculum sampled uniformly without targeting?

The hypothesis expects higher sample efficiency from targeting because generated tasks concentrate on error modes the base model actually exhibits rather than spending capacity on tasks it already solves or rarely encounters.

Answering this requires training and evaluating matched treatment and control cohorts under identical hyperparameters, compute limits, and pipeline quality controls. That training and evaluation run was never completed before the repository was frozen, so no outcome is reported here.

3.Background and motivation

Curriculum learning assumes that example selection and ordering alter what a model learns per unit of compute. Automated verification offers a way to scale synthetic code data without relying strictly on human-written problem sets, because differential tests and reference checks filter out broken solutions before training.

VGCL combines these two components in a controlled setting. Instead of asking whether synthetic data helps in general, the pipeline isolates the selection policy: given identical generators, verifiers, and budget, does steering generation toward measured model errors beat uniform coverage across problem subtypes? Similar combinations of search, verification, and iterative training exist elsewhere in program synthesis and formal reasoning, though at different scales and with stronger formal guarantees than the behavioral checks used here.

4.Experimental design

The planned experiment compares two curriculum conditions under a shared compute budget:

  • Treatment: verified synthetic programming problems generated to target failure clusters observed on the base model.
  • Control: verified synthetic programming problems generated round-robin across six Monotonic Queue / Deque subtypes without failure targeting.

Both conditions share the same generation model, repair pass, differential oracle, and structural deduplication machinery. The intended experimental contrast is solely the targeting mechanism. As frozen, the repository implements cohort generation, probing, gating, and provenance tracking, but stops short of training or evaluating models on either cohort.

5.Final VGCL architecture

V7 organizes execution into three stages split between a local workstation and a remote GPU runner on Kaggle.

Local generation and verification
API generation→ Syntax / repair→ Reference-independence screening→ Subtype validation→ Phase A verification→ Phase B verification→ Structural deduplication→ Ledger / manifest staging→ PENDING_KAGGLE_PROBE
↓ manifest transferred to Kaggle
Remote probing on Kaggle
Manifest→ Qwen/Qwen2.5-1.5B-Instruct→ Pass@1 / Pass@10 probing→ Isolated sandbox eval→ Probe result
↓ probe result returned locally
Local ingestion
Probe result→ Integrity / provenance checks→ Target validation→ Primary eligibility→ Approved / auxiliary

Generation and candidate verification run locally one item at a time. An API call generates a task specification, an optimized solution, a test generator, and a separate reference solution. The package undergoes syntax repair, reference-independence screening, subtype checks, two behavioral verification phases, and structural deduplication before being queued in a manifest marked PENDING_KAGGLE_PROBE.

Remote probing loads Qwen/Qwen2.5-1.5B-Instruct, samples completions under the Pass@1 and Pass@10 protocol, and evaluates every generated solution alongside its test generator and reference inside a centralized sandbox (isolated_executor.py). Probe results return to local ingestion for hash verification, target validation, and primary eligibility gating into approved or auxiliary pools.

6.Model roles

Four model roles exist in the pipeline and are kept separate by configuration and prompt boundary.

Role Model / mechanism
Generator gemini-3.6-flash
Fallback generators gemini-3.1-flash-lite, gemini-3.5-flash-lite, gemini-flash-latest
Base / probe model Qwen/Qwen2.5-1.5B-Instruct
Reference Separate API call under the generator policy, prompt-isolated from the optimized solution
Trained model None present in the frozen repository

The Gemini models generate tasks, references, and test suites; Qwen only generates candidate solutions during probing. No fine-tuned checkpoint from VGCL curriculum data exists in the repository.

7.Failure targeting

Failure targeting links generation to observed model errors by categorizing runtime failures on probes and checking whether newly generated tasks trigger the requested failure category.

Failure clusters

Eight failure clusters label observed runtime outcomes during execution. They describe test behavior only and make no claim about internal model circuits or latent representations.

Cluster Runtime condition Known probing limit
FC_01_MICRO_CORRECTNESS Incorrect output on small-scale inputs Can absorb unrelated small-scale exceptions or errors
FC_02_SCALE_DIVERGENCE Breaks down as input scale increases Under-exercised because probing runs small-scale cases
FC_03_TERMINATION Exceeds execution time limit or fails to finish cleanly Wall-clock timeouts stop hung code, though slow algorithms still map to the same cluster as infinite loops
FC_04_BOUNDS_VIOLATION Violates declared input or output bounds None noted
FC_05_RESOURCE_FAILURE Exceeds memory or runtime resource limits Large-scale resource triggers rarely reached on small probes
FC_06_FORMAT_CONTRACT Violates expected return type or shape None noted
FC_07_STATE_INCONSISTENCY Produces inconsistent output across stateful calls Multi-call state checks are absent in standard small probes
FC_08_UNKNOWN Failures outside the categories above Can be shadowed by small-scale fallback classification

Sandbox initialization and infrastructure errors (SandboxInfrastructureError) propagate as operational failures rather than being coerced into candidate failure clusters or false Pass@1=0 observations.

Target validation

Asking a generator for an FC_01 problem only records intent. A candidate enters the validated targeted pool only after Qwen runs on it, fails, and yields a failure cluster matching the request. Earlier pipeline versions treated the requested label as sufficient on its own.

Merge-step trust gap: merge_probe_results.py accepts the declared target-validation status attached to incoming probe metadata rather than recomputing the failure classification from raw execution traces during ingestion. Target authenticity improved once observed probing became mandatory, though local ingestion still trusts the probe-side label assignment.

8.Base-model probing

Probing evaluates Qwen/Qwen2.5-1.5B-Instruct on each staged item under two sampling settings:

  • Pass@1: one greedy completion.
  • Pass@10: one greedy completion plus nine sampled completions at temperature 0.8 and top-p 0.95 (k = 10).

difficulty = 1.0 − pass@10

In the implementation, pass@10 is binary per item: 1.0 if any of the ten attempts passes, 0.0 if all ten fail. Item difficulty is therefore binary (0.0 or 1.0) rather than a continuous pass rate across ten samples.

Model and tokenizer loading in base_model_prober.py, phase0_calibration/extract_trajectories.py, and phase0_calibration/prepare_calibration_data.py sets trust_remote_code=False, relying on native Hugging Face Qwen2ForCausalLM support rather than executing remote repository code. In kaggle_probe.py, execution checks get_active_sandbox() before downloading or loading model weights and fails closed if no compliant isolation backend is available.

Default execution blocks local Qwen loading through a probe guard so GPU probing runs remotely, though explicit overrides exist for controlled local runs and calibration utilities load the model directly.

Several provenance fields are missing from probing logs, limiting exact bitwise reproduction of past Kaggle runs:

  • Model weight SHA-256 hash
  • Tokenizer hash
  • Full library and CUDA dependency versions
  • GPU hardware model
  • Complete RNG state across sampling
  • Full text of all sampled completions
  • Complete stopping specification

9.Verification and candidate quality

Generated candidates go through behavioral checks and structural screens rather than formal program proofs.

Phase A and Phase B

In oracle_refactor.py (and the legacy verifier path), Phase A tests the optimized solution differentially against the brute-force reference on generated small inputs. Phase B runs the optimized solution alone on larger inputs and compares observed timing and AST complexity heuristics against declared constraints. Neither phase provides formal correctness guarantees, Phase B lacks a reference check at large scale, and minimum large-case input sizes are not strictly enforced across every generator.

Isolated execution boundary

In V7, behavioral verification ran via standard multiprocessing and in-process exec() with AST checks and Python socket monkey-patching. In V8, all untrusted execution paths in base_model_prober.py, oracle_refactor.py, legacy/verifier.py, and legacy/audit_curriculum.py were consolidated into isolated_executor.py.

Test generators, optimized solutions, and brute-force references now execute in separate sandbox invocations, with differential comparison performed by the trusted parent over bounded, tagged JSON IPC instead of pickle. Each invocation uses a three-process split (non-dumpable supervisor, non-dumpable trusted runner, and candidate) with per-run nonce authentication so the untrusted child never holds the supervisor response descriptor and cannot set passed, execution_time, or memory_mb.

Two fail-closed backends are supported via VGCL_SANDBOX_BACKEND (auto, container, or linux_ns), with process-only and in-process fallbacks removed:

  • Container backend: Docker or Podman using a digest-pinned Python image (--pull=never, --network none, --read-only, --cap-drop ALL, no-new-privileges, --ipc none, UID/GID 65534, memory/swap/CPU/PID/FD limits, zero host bind mounts, forced rm -f removal on timeout, OCI default seccomp).
  • Linux namespace backend: unprivileged user, network, PID, and mount namespaces with a read-only minimal root via pivot_root, private /proc, minimal /dev, private tmpfs /tmp, PR_SET_PDEATHSIG, PR_SET_DUMPABLE=0, PR_SET_NO_NEW_PRIVS=1, resource limits, and an architecture-specific seccomp-BPF filter blocking network syscalls and nested namespace creation.

Residual isolation limits remain documented: both backends share the host kernel; candidates under the Linux namespace backend map as UID 0 inside their user namespace (making theoretical /proc/<pid>/mem inspection of the runner possible under --map-root-user, even with ptrace and process_vm_readv/writev seccomp-blocked); container execution uses OCI default seccomp rather than VGCL's custom BPF filter; and per_case_times inside Phase B remains candidate-reported within runner-enforced total wall-clock limits.

Reference independence

Reference implementations are generated in a separate prompt-isolated API call and screened against the optimized solution, rejecting pairs whose structural similarity exceeds 0.85. Structural dissimilarity shows the two functions differ syntactically, but does not rule out shared algorithmic misunderstandings or correlated provider priors.

Deduplication

Candidates are compared using normalized ASTs, control-flow graphs, hashes, and 4-gram Jaccard similarity with a 0.70 rejection threshold. Deduplication state lives in memory per invocation, meaning separate runs do not deduplicate against one another. Targeted and uniform pipelines also run separate deduplication instances, no deduplication runs against external evaluation benchmarks, and rejected duplicates stay in the per-run index and continue to influence later similarity checks.

10.Treatment and uniform control

The control arm is uniform over a closed schedule rather than over all possible programs: generation cycles round-robin across six Monotonic Queue / Deque algorithmic subtypes (Types A through F).

Control and treatment share the same generator backend, repair logic, oracle checks, and ledger schema. They differ in prompt framing, absence of failure-cluster targeting, subtype rotation schedule, seed ranges, and eligibility metadata.

Eligibility gates

Uniform items require quality verification and receive control status UNIFORM_CONTROL with target status NOT_APPLICABLE. Targeted primary items must clear thirteen conditions:

  • Phase A verification passed
  • Phase B verification passed
  • Structural hash present
  • Structural similarity below 0.70 threshold
  • No manual reviewer override
  • Neither pass used a fallback generator
  • Primary generator produced both passes
  • Recorded generator policy matches expected policy
  • Canonical subtype label
  • Target validation status equals VALIDATED
  • Non-empty probe-result SHA-256 hash
  • Parseable failure evidence payload
  • Generated subtype matches requested subtype

Even with this gate in place, no completed final dataset demonstrates that realized treatment and control pools are matched on empirical difficulty, token length, or subtype proportions. Isolating targeting as the sole difference between arms remains a design intent rather than an observed property of finished cohorts.

11.Provenance, leakage, and dataset integrity

Fallbacks

When API quotas or transient faults interrupt generation, requests can route to fallback models (gemini-3.1-flash-lite, gemini-3.5-flash-lite, or gemini-flash-latest). Because the optimized and reference passes invoke the API separately, a single item can mix models. Primary eligibility rejects any item flagged with fallback usage. Historical archived runs contain fallback-mixed items; because no final training cohort was assembled, purity of a finished experiment population is enforced in code but unobserved on final data.

Leakage

Earlier calibration files overlapped with evaluation material. Current calibration data draws from MBPP training data while keeping the older contaminated file archived separately. An ID-overlap guard blocks matching identifiers between calibration and evaluation sets, though ID disjointness alone cannot detect near-duplicate problem statements filed under distinct IDs.

Ledger

The SQLite ledger tracks candidate generation, verification, probing, and eligibility outcomes. It uses INSERT OR REPLACE semantics, allows in-place row replacement rather than append-only writes, lacks full foreign-key enforcement across tables, permits duplicate JSONL entries, does not hash full candidate packages end-to-end, and omits complete prompt coverage.

Hashes

SHA-256 hashes detect accidental corruption or drift across canonicalized fields. They verify content matching against a recorded digest rather than providing cryptographic authentication of origin or authorship.

12.Statistical analysis framework

The module statistical_analysis.py contains planning utilities that take design parameters such as an assumed intraclass correlation (ρ = 0.20) and design effect to estimate sample sizes before data collection. Those numbers are prior design inputs rather than empirical power or effect-size measurements from an actual run.

Implementation bug: statistical_analysis.py labels a normal-tail approximation as a permutation-test p-value, without running permutations and without passing its calculated Welch degrees of freedom into a Student-t distribution. Because no experiment cohort reached analysis, this helper bug did not affect any published result, though it would need fixing before analyzing real trial data.

13.What the audits revealed

Across versions V1 through V8, the repository changed mainly in response to failure modes uncovered by auditing earlier runs:

  • Early generation targeted algorithm categories by name, which produced valid exercises without verifying whether the base model actually failed on them.
  • Difficulty scores originally depended on synthetic heuristics or pseudo-random assignment rather than observed Qwen probes.
  • Requested failure targets were trusted as labels before probe behavior confirmed them, and generated problems drifted away from requested subtypes.
  • Treatment and control cohorts differed on auxiliary prompt and fallback paths beyond targeting alone.
  • Earlier calibration splits shared overlap with evaluation material, and provenance hashes lacked end-to-end linkage.
  • Security auditing in V8 found untrusted candidate execution inside the model process via exec(), pickle IPC in oracle workers, mutable container assumptions, inverted seccomp-BPF jump logic in an intermediate patch, forgeable worker response pipes, and trust_remote_code=True on model loading.

V7 consolidated the methodological and gating repairs; V8 closed the execution-boundary findings without modifying prompts, probing logic, or curriculum eligibility rules.

14.Final frozen state

Two milestone tags define the archived state of tazwaryayyyy/VGCL_Pipeline:

  • V7 research methodology freeze (11 September 2026): tag phase0-experiment-freeze-v7, commit 98398d6e49736d83fa3c39560d4d556a8a760419, followed by documentation commit acbea49.
  • V8 security hardening freeze (19 November 2026): tag phase0-experiment-freeze-v8, commit 126ed4351ef2a7176b94004babaafb2ad7dad968, introducing centralized fail-closed sandbox execution and model-loading restrictions.

Under V7 alone, test_phase0_pipeline.py passed all 77 unittest cases. Following the V8 security update, the combined regression suite (test_phase0_pipeline.py, test_security_sandbox.py with 94 security tests, and legacy suites configured in pytest.ini, totaling 179 tests) passed in GitHub Actions (.github/workflows/security-tests.yml) across Ubuntu 22.04 (Python 3.10, 3.11, and 3.12 with both linux_ns and container backends and VGCL_REQUIRE_SANDBOX=1) and on Windows Server for fail-closed policy enforcement without a container runtime. Local validation also passed (170 passed, 9 Linux-only seccomp tests skipped on Windows 10 with Docker Desktop; 179 passed, 0 skipped on Linux 6.x WSL2 with linux_ns). No live Kaggle probing run or full GPU training experiment was run after V8 hardening.

Passing software regression tests verifies deterministic code paths, serialization validation, and sandbox boundaries. It does not substitute for empirical training runs or demonstrate model capability gains.

16.Scientific status

Because the training and evaluation comparison between targeted and uniform curricula was never run, the repository does not support any claim about empirical performance:

  • That VGCL improved or failed to improve model capability
  • That VGCL had zero effect
  • That failure targeting outperformed or underperformed uniform sampling
  • Any effect size, confidence interval, or p-value
  • Out-of-distribution generalization or mechanistic insight

What remains in the repository is engineering and experimental groundwork: a documented local-and-remote pipeline, failure modes caught across V1 through V8 audits, an isolated fail-closed execution layer, and a complete protocol ready if a future trial is run.

17.Repository and reproducibility

The repository is frozen at tazwaryayyyy/VGCL_Pipeline, anchored at tag phase0-experiment-freeze-v7 (98398d6e49736d83fa3c39560d4d556a8a760419) for the experimental design and tag phase0-experiment-freeze-v8 (126ed4351ef2a7176b94004babaafb2ad7dad968) for the hardened execution layer.

Software claims (gating rules, ledger schema, IPC codec, seccomp policy simulation, and sandbox boundaries) can be reproduced locally via pytest on Linux (with unprivileged user namespaces or Docker/Podman and the pinned Python digest image) or on Windows with Docker Desktop.

Kaggle probing runs remain only approximately reproducible because weight hashes, hardware identity, and full RNG state were not logged in V7. No trained model weights or completed experimental datasets exist in the repository.
